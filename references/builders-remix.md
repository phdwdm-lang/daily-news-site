# Builders 中文整理规则

这是总 Skill 自带的固定整理规则。采集器直接读取本文件，不远程下载提示，不依赖其他本地 Skill、个人配置或自定义提示目录。

## 输入与完整性

- 唯一正文来源是本次 `raw.json` 里的 `x`、`podcasts`、`blogs`。保留公开聚合 feed 返回的实际内容，不另去 X 补抓正文，不根据标题、作者知名度或个人兴趣筛掉人物。
- 全部返回人物都须进入 Builders 数据；每人全部返回推文都须有独立原帖入口和真实发布时间。当前返回数量动态计算，不能写死为十一人或二十一条，也不能为了卡片数量减少人物或原帖。
- 每个人的姓名、账号、角色依据本次 feed 的 `name`、`handle`、`bio`。没有角色时留空，不补写推测的公司或职位。
- 原帖正文和元数据完整保存在原始采集文件中。页面可用精简中文表达，但不能删掉返回人物或原帖入口；所有概括必须能逐句回溯。
- `fetchedAt` 表示本次取回时间，feed 的 `generatedAt` 表示上游生成时间，`createdAt` / `publishedAt` 表示内容真实发表时间，三者分别记录。不能把抓取日期或日报日期冒充内容发布日期；上游下午更新也不代表全部帖子发表于当天。
- `feedStatus` 非 `ok` 时不能称为完整成功。不得把旧文件作为本次新采集结果；若要保留网站旧版，明确标记本次失败及保留旧版的原因。

## 人物卡片

1. 用一句中文抓住这位作者本次内容的核心，再用两至四句完整中文整理观点、产品、技术讨论或经验；不要用“能力 / 入口”分点标签拆句。
2. 多条帖文可以归为同一观点，但所有原帖都必须保留入口和各自真实时间。帖子实际内容不同则分开说明，不能拼成作者未曾表达的新主张。
3. 个人生活、活动宣传、无实质评论的转发等，明确用一句话说明性质；仍保留作者和原帖，不用“没更新”掩盖不感兴趣的内容。
4. 如果某人的全部返回内容没有实质可总结信息，写明“本次返回内容以简短回应或宣传为主”，并保留全部来源，不填充臆测。
5. 引用帖或回复依赖未提供上下文时，明确注明“聚合源未提供被引用内容 / 上下文”，仅概括当前可见正文。不能根据短链、表情或一句预告推测发布的产品能力。
6. 原文中的预测、个人体验、未发布计划、第三方说法要保持归属与不确定性，不能改写为已证实事实。
7. 展示标题使用中文，专有产品名保留原名。姓名可保留原语言。头像按身份核实后缓存；找不到时留空并显示姓名首字母，不借用他人头像。

## 播客与博客

- 所有返回条目先进入整理台账；可展示、缺失字段、重复、旧内容分别说明，不能静默丢失。
- 播客正文只根据提供的完整 transcript 概括，先给一句核心结论，再解释人物背景与具体观点。实际页面标题必须是准确中文标题，原始英文标题保存在数据中。
- 播客必须具备可核实的单期链接和真实发表时间。只有播放列表、缺失转录、或无法核实具体节目时，保留原始返回并记录阻断原因，不伪造节目链接，不把旧节目称为今天新发布。
- 博客以原始文章标题、发布者和直达链接为依据；优先产品、功能或研究的具体变化及影响。全文不足时注明内容范围，不把标题猜测当正文。
- 不强制逐字引用。需要引用时必须来自实际给出的正文，准确归属，并遵守来源引用长度限制。

## 发布前必须验证

- 页面 Builders 人物身份集合与本次 `x` 一致，不能只验证数量。
- 每个人的原帖 URL 集合与 feed 一致，每条时间与原始字段一致；无 URL、无时间的输入显式报错或标记缺失，不能编造。
- 头像、中文概括、人物身份逐一对应；引用缺上下文的说明不能在润色时消失。
- 将采集时间、每个 feed 的生成时间、实际人物数、原帖数、播客 / 博客数，以及缺失 / 失败状态保存到本期运行记录。
